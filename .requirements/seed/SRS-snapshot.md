## Architecture Note — Two Front Ends (v1)

v1 ships as **two Next.js front ends sharing one database, one Clerk application, and one shared backend data layer**:

- **`apps/portal`** — "Client Portal". Public services browsing, engagement request form, client sign-in/sign-up, and all signed-in client workflows (onboarding, file exchange, messaging, history).
- **`apps/admin`** — "Tax Portal". Accountant-only surface (dashboard, pipeline, client/engagement management, admin UI for services catalog, intake templates, engagement letter template).

Role-based middleware gates on each app enforce access boundaries before any route handler runs. A signed-in CLIENT navigating to `apps/admin` is redirected to `apps/portal`; an ACCOUNTANT navigating to `apps/portal` CLIENT-only routes is redirected to `apps/admin`. Public routes on `apps/portal` (services page, request form, sign-in, sign-up completion) remain reachable unauthenticated.

Cross-reference: **ADR-006** (monorepo layout and two-app structure), **ADR-010** (cross-app navigation and session boundaries).

Requirements in this SRS are written in terms of system behavior, not app directory. Where a requirement applies to a specific surface, the app is noted in the requirement row.

## 1. Product Overview

A custom web portal for a solo tax accountant to engage clients for tax services, communicate throughout the process, and exchange files securely — replacing email as the primary client-facing channel. The accountant uses it as her daily work surface to track and manage all client engagements.

**Key differentiator:** self-initiated engagement from a public front door. Prospective clients browse services and submit engagement requests without an account. The accountant reviews and accepts or declines — then onboarding begins.

**What this is not:** a tax preparation, calculation, or filing tool. No IRS integrations, no payment processing, no scheduling.

---

## 2. Users & Roles

| Role | Description | Account creation |
|---|---|---|
| **ACCOUNTANT** | Solo tax practitioner. One instance. Full admin visibility across all clients and engagements. Primary surface: `apps/admin` (Tax Portal). | Pre-created; single account. |
| **CLIENT** | An invited client with a portal account. Sees only their own engagements and data. Primary surface: `apps/portal` (Client Portal). | Invitation-only — account created after accountant accepts engagement request. |
| **Anonymous** | Prospective client. No account. Access limited to the public services page and engagement request form on `apps/portal`. | N/A |

### LIFE — Engagement Lifecycle

| ID | Requirement | Status | Notes |
|---|---|---|---|
| REQ-LIFE-001 | Engagements follow a four-stage status pipeline: `New → In Progress → Review → Complete`. | Planned | |
| REQ-LIFE-002 | Client-facing status labels are simplified and friendly — they differ from internal labels. | Planned | **Clarification needed (CLARIF-002):** The exact labels must be defined before the engagement lifecycle epic ships. |
| REQ-LIFE-003 | Status transitions are manual — the accountant moves engagements through stages (v1). No automated transitions except the onboarding-completion trigger (REQ-ONBD-006). | Planned | |
| REQ-LIFE-004 | `Review` is an internal accountant status meaning she is reviewing her own work before delivering to the client. It is not a client-facing review step. | Planned | |
| REQ-LIFE-005 | `Complete` requires two explicit accountant actions: (1) mark return as delivered to client AND (2) mark return as filed with IRS. Both must be confirmed before the engagement can be marked Complete. | Planned | |
| REQ-LIFE-006 | Only the accountant can reopen a completed engagement (e.g., for an amended return). Clients cannot reopen. | Planned | |
| REQ-LIFE-007 | Each engagement has a due date set by the accountant. | Planned | |
| REQ-LIFE-008 | Each engagement has internal notes visible only to the accountant. | Planned | |
| REQ-LIFE-009 | Each engagement can be flagged / prioritized by the accountant. | Planned | |
| REQ-LIFE-010 | A client may have multiple concurrent engagements for different service types. | Planned | |
| REQ-LIFE-011 | Only one engagement per service type per tax year per client is permitted. | Planned | **Clarification needed (CLARIF-003):** What should the system do when a duplicate is attempted — silent block, error message, or redirect to the existing engagement? |
| REQ-LIFE-012 | An engagement may have multiple participants (e.g., spouses). Participants are separate portal accounts linked to the engagement. | Planned | See REQ-AUTH-007. |

## 5. Data Model Overview

Canonical data models are defined here from the intake. The SA and developer agents will refine these into Prisma schema definitions. Cross-reference with intake.md § "Core data models."

| Model | Key Fields |
|---|---|
| `User` | `clerkId`, `role` (ACCOUNTANT/CLIENT), `email`, `name` |
| `Service` | `title`, `description`, `estimatedTimeline`, `isActive` |
| `EngagementRequest` | `serviceIds[]`, `contactInfo`, `status` (pending/accepted/declined), `declineMessage` |
| `Engagement` | `clientId`, `serviceId`, `status`, `taxYear`, `dueDate`, `internalNotes`, `priority`, `completedDelivered`, `completedFiled` |
| `EngagementParticipant` | `engagementId`, `userId` |
| `OnboardingState` | `engagementId`, `letterSigned`, `questionnaireDone`, `initialDocsUploaded` |
| `IntakeTemplate` | `serviceId`, `questions[]` |
| `Thread` | `clientId`, `engagementId` (nullable), `type` (engagement/general) |
| `Message` | `threadId`, `senderId`, `body`, `attachments[]`, `readAt` |
| `Document` | `engagementId`, `folderId`, `uploadedById`, `storagePath`, `label`, `version`, `deletedAt` |
| `Folder` | `engagementId`, `name`, `createdById` |
| `DocumentRequest` | `engagementId`, `label`, `dueDate`, `fulfilledAt` |
| `Notification` | `userId`, `type`, `engagementId`, `readAt`, `payload` (JSON) |
| `NotificationPreference` | `userId`, `emailEnabled`, `overdueReminderDays` |

> Note: The intake listed `Message` with an `engagementId (nullable)` field. The RA has reorganized this with a `Thread` model as the parent, and `Message.threadId` as the foreign key, to properly support general (non-engagement-scoped) threads per REQ-MSG-002. The SA should review this during architecture planning.

## 6. Out of Scope (v1)

- Firm branding (logo, colors, firm name) — deferred to v2
- Terms of service / privacy policy pages — deferred to v2
- Payment processing / invoicing
- Tax calculation or preparation tools
- IRS e-filing integration
- Calendar / scheduling / discovery calls
- Multi-staff / employee accounts
- Mobile native app
- Email marketing or newsletters
- Automated status transitions (v1 is manual only, except onboarding completion trigger)
